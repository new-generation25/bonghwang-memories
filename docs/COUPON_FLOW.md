# 쿠폰과 포인트 — 한 장 요약

**2026-08-02 기준.** 값은 전부 코드에서 옮겨 적었다. 숫자가 의심스러우면
`src/lib/points.ts` · `src/lib/coupons.ts` · `src/lib/coverage.ts`가 원본이다.

> **올해는 시범운영이다.** 모든 가게가 무료이고 충당률 0%다 — 할인액을
> 운영사가 전액 부담한다. 구독이 시작될 자리(기본 1만 / 프리미엄 3만)는
> 미리 세워 두었지만 켜지 않았다.

---

## 1. 두 가지 혜택, 한 가지 길

| | 쿠폰 | 포인트 |
|---|---|---|
| 성격 | 확정 혜택 — 무엇을 받을지 정해져 있다 | 누적 리워드 — 금액을 카운터에서 정한다 |
| 단위 | 액면(원) | 1p = 1원 |
| 받는 법 | 거점 미션 완료 · 뽑기 | 미션·빙고·완주·설문 등 |
| 쓰는 법 | **가게 스티커를 손님이 찍는다** | **같다** |

**쓰는 길이 하나다.** 가게는 카운터에 스티커 한 장만 두면 되고 기기도
로그인도 필요 없다. 사장님이 보시는 것은 손님 화면의 「사용 완료」 하나다.

```
손님이 스티커 QR을 찍는다 (또는 인쇄된 8자리를 손으로 넣는다)
        ↓
확인 화면 — 가게 이름 · 혜택 · "한 번 쓰면 되돌릴 수 없어요"
        ↓
[사용하기] → 「✓ 사용 완료」 → 사장님께 보여드린다
```

- **찍었다고 바로 쓰이지 않는다.** 카메라는 손에 들고 있으면 저 혼자
  읽으므로, 스티커 근처에서 켜 둔 것만으로 쿠폰이 없어지던 일이 있었다
- **지갑에 든 사람만 쓴다.** 규칙이 사용 기록의 uid를 요청 계정과 대조한다.
  캡처를 남에게 보내도 그 사람은 쓸 수 없다
- 가게 주도로 처리하는 화면은 없앴다. `/shop/verify`는 인쇄물에 주소가
  적혀 있어 안내만 남기고 사용 내역으로 보낸다

## 2. 쿠폰 — 무엇이 있나

### 거점 쿠폰 (미션을 끝내면 그 자리에서)

| id | 가게 | 혜택 | 액면 |
|---|---|---|---|
| `cp1` | 봉황1935 | 음료 1,000원 할인 | 1,000원 |
| `cp2` | 미야상회 | 바나나우유 500원 할인 | 500원 |
| `cp3` | 능소화 고택 | 엽서 1장 증정 | 1,000원 |
| `cp4` | 카페 탱자 | 아메리카노 1,000원 할인 | 1,000원 |
| `cp5` | 방하림 | 도자기 1,000원 할인 | 1,000원 |

미션 정의(`TRACK_MISSIONS`)의 `reward.coupon`을 `dispatchAction()` 한 곳에서
읽어 준다. 화면은 여섯 갈래(개수·사진·AR·퀴즈·녹음·해제)지만 완료 신호가
그 함수로 모이므로, 화면마다 붙이면 새 미션에서 빠뜨린다.

`addCoupon()`이 중복을 막아 다시듣기(D9)로 액션이 또 와도 두 장이 되지 않는다.

**쿠폰은 서버가 발행하지 않는다.** 거점을 통과하면 기기에 `cp1`이 담기고,
로그인해 두었으면 진행 기록과 함께 서버로 올라간다. 코드는 사용하는 순간
만들어진다 — `couponSerial()`이 uid와 쿠폰 id로 번호를 뽑는다.

### 뽑기 쿠폰 (「추억의 뽑기왕」 판에서)

가게 쿠폰(`gcTangja`·`gcBonghwang`), 협력 카페 공용권(`gcCafe`·`gcCafe2`),
안내소 물건(엽서·스티커·간식·폴라로이드·믹스테이프).

> 공용 할인권 두 종은 **뽑기 판에서 뺐다** — 어느 카페에서 쓰는지 카드 한
> 장으로 설명할 수 없고, 협력 가게가 바뀌면 이미 나간 쿠폰의 뜻이 함께
> 바뀐다. 카탈로그에는 남겨 두었다(보너스 미션 보상 후보).

### 받는 흐름

```
빙고 한 줄  →  뽑기 한판 한 장  →  판에서 칸 하나  →  쿠폰 또는 포인트
```

보상 자리를 하나로 모은 것이다. 예전에는 첫 줄에서 가게 쿠폰 다섯 장을
한꺼번에 줬는데, 무엇을 하면 무엇을 받는지가 흐려졌다.

> ⚠️ **뽑기 상품표를 바꾸면 판이 다시 섞인다.** `boardFor()`가
> `GACHA_PRIZES`에서 파생하므로 이미 뽑은 칸이 다른 상품을 가리키게 된다.
> 실판매 뒤에는 건드리지 마라.

## 3. 포인트

### 배점

| 사유 | 값 |
|---|---|
| 메인 미션 한 칸 | 100p |
| 보너스 미션(빙고 칸) 한 칸 | 100p |
| 빙고 한 줄 | 500p |
| 코스 완주 | 200p |
| 스페셜(B면 해제) | 100p |
| 나의 기록 공유 | 100p |
| 완주 설문 | 200p |
| 캠페인 · 뽑기 당첨 | 동적 — `awardDynamic()`, 한 번에 최대 1,000p |

**칸은 칸이라 메인과 보너스의 값이 같다.**

### 규칙

- **1p = 1원**
- **사용 문턱 3,000p** — 미만이면 "3,000p부터 사용 가능, 현재 1,800p"처럼
  남은 양을 보여준다
- **유효기간 6개월** — 적립일 기준. 먼저 받은 것부터 소진한다(FIFO)
- **만료 배치를 두지 않는다.** `pointWallet()`이 읽을 때마다 판정한다.
  원장에서 지우면 왜 줄었는지 답할 근거가 없고, 기기마다 지운 시점이 달라
  서버와 합칠 때 어긋난다
- 소멸분은 회계상 부채로 잡지 않는다

### 원장

적립도 차감도 `users/{uid}/points`에 쌓인다. 문서 id가 `refId`라 같은 미션을
두 번 완료해도 덮어쓰기가 되어 중복 적립이 안 된다. **적립 건을 깎지 않고
음수 건을 따로 남기는 것**은, 얼마를 받았고 얼마를 썼는지 나중에 되짚을 수
있어야 하기 때문이다. 잔액은 읽을 때 합산한다.

**무결제 적립을 막지 않는다.** 코스를 결제하지 않은 사람도 보너스 미션만
수행해 포인트를 쌓을 수 있다 — 인근 주민의 재방문을 만드는 동선이다.

## 4. 충당률과 정산 (가게·운영사 사이)

**참여자에게는 보이지 않는다.** 화면에는 쿠폰 액면과 포인트 잔액만 있고,
누가 얼마를 부담하는지는 관리자·사장님 화면에만 있다. E2E가 참여자 화면에
'충당'이라는 글자가 없는지 검사한다.

### 등급

| 등급 | 충당률 | 월 회비 | 월 상한 |
|---|---|---|---|
| 무료 | **0%** | 0원 | 30,000원 |
| 기본 협력 | **0%** (협의값 60%) | 10,000원 | 30,000원 |
| 프리미엄 | **0%** (협의값 85%) | 30,000원 | 60,000원 |

굵은 값이 지금 켜져 있는 것이다. 협의값은 주석에만 있다 — 판이 무엇인지
보여드리기도 전에 청구서부터 보내면 다음 해에 남을 가게가 없다.

**신규 3개월 유예는 두지 않았다.** 시간이 저 혼자 등급을 올리면 아무도
누르지 않았는데 가게 부담이 는다.

### 산식

```
사용 금액     = 쿠폰 액면 또는 사용 포인트 (1p = 1원)
가게 부담액   = 사용 금액 × 충당률
운영사 부담액 = 사용 금액 × (1 − 충당률)
```

### 스냅샷 — 이 설계의 핵심

**사용 시점의 충당률과 분담액을 기록에 값으로 복사한다.** 정산할 때
가게 문서의 율을 조인해 계산하면, 등급이 바뀌는 순간 지난 달 청구서가
함께 움직인다.

참여자 기기는 가게 문서를 읽을 수 없다(읽히면 스티커 토큰이 샌다).
그래서 **율을 비운 채 기록을 만들고, 율을 아는 기기가 나중에 찍는다**
(`stampPending()`). 율이 바뀐 뒤의 기록은 찍지 않고 남겨 관리자가 판단한다
(`rateSince`).

> 그래서 아직 안 찍힌 기록이 있으면 **운영사 부담이 0원으로 보인다.**
> 관리자 화면의 「미반영 N건 채우기」가 그것을 메운다.

### 월 상한은 사용을 막지 않는다

명세는 상한에 닿으면 그 달의 사용을 차단하라고 했지만 **그렇게 하지 않았다.**
상한에 닿을 만큼 쓴 참여자는 그만큼 자주 온 손님이고, 카운터에서 돌려보내면
그 손님을 잃는다. 넘은 몫은 청구에서 빠지고 **운영사가 진다.**

- 상한의 80%를 넘으면 사장님 화면에 알린다
- 운영사 부담이 당월 매출의 3%를 넘으면 관리자 화면에 경고 (리워드 예산 천장)

### 정산

- 월 1회. 마감은 관리자 화면의 버튼이 한다 (돌릴 서버가 없다)
- 청구액 = 월 회비 + 당월 충당액 합계
- 사장님 화면에는 **충당액과 매출 유입액을 나란히** 둔다. "얼마를 냈는가"만
  보면 이탈하고, "얼마를 받았는가"를 함께 봐야 유지된다
- 가게 충당액은 매출이 아니라 **운영사 원가의 차감 항목**이다.
  비용 계정에는 운영사 부담액만 올린다

## 5. 배포 없이 바뀌는 값

| 문서 | 무엇 | 누가 읽나 |
|---|---|---|
| `config/points` | 배점 · 문턱 · 유효기간 | **공개** — 참여자 화면이 읽는다 |
| `config/settlement` | 등급별 충당률 · 회비 · 상한 | **관리자만** |

문서를 둘로 가른 것은 읽는 사람이 다르기 때문이다. 충당률이 새면 가게끼리
서로의 계약 조건을 알게 된다.

---

## 6. 아직 안 된 것

- **결제 흐름이 없다.** 등급 고정 상품(5천원→굿즈, 1만원→5천원 할인쿠폰)이
  나갈 자리가 아직 없다. 쿠폰 액면 4,500원은 2단 상품 기준으로 세워둔 값이다
- **보너스 미션에서는 포인트만 준다** — 쿠폰은 아직 안 나간다
- **혜택 사용 계측이 없다.** `coupon_used`·`points_used` 이벤트 이름은
  정의돼 있는데 부르는 자리가 없어서, 받고도 안 쓰는 구간을 퍼널에서 못 본다
- 운영에서 관리자 화면의 「🔧 빠진 칸 채우기」를 아직 누르지 않았다 —
  시드된 가게 문서에 `accepts`·`groupCoupons`가 없어 그룹·뽑기 쿠폰이
  교환 시점에 거절된다

## 검증 도구

```bash
npm run check:settlement   # 분담 산식·지갑 계산 (E2E가 못 보는 자리)
npm run test:rules         # firestore 규칙 29개 (에뮬레이터)
npm run check:redeem       # 앱 코드를 에뮬레이터에 붙여 사용을 끝까지 14개
```

`check:settlement`가 따로 있는 이유 — E2E는 화면이 무엇을 보여주는지 보지,
4,500원의 60%가 2,700원인지는 보지 못한다. 그 계산이 틀리면 아무도 안 죽고
화면도 멀쩡한 채로 청구서만 틀린다.
